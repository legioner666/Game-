# 09. Технічна архітектура, моделі даних і стартові числа

Статус: проєкт технічного рішення v0.4 із середнім темпом і зонами складності. Реалізація ще не створена. Пов'язані рішення: D-03, D-05, D-09, D-11, D-12, D-21–D-23.

## 1. Рушій і структура репозиторію

На перевіреному `main` Crown Rush має конфігурацію Godot 4.4; Android workflow використовує 4.4.1. Для першого прототипу пропонується той самий зафіксований інструментарій. Це вибір для зменшення початкової інтеграційної роботи, а не твердження про найновішу версію рушія.

До створення коду підтверджуємо D-21: Godot 3D або інший узгоджений стек. Порівняння рушіїв потребуватиме окремого короткого прототипу лише за наявності конкретної проблеми.

| Майбутній каталог | Вміст |
| --- | --- |
| `parasite-evolution/` | Корінь нового проєкту з власним `project.godot` |
| `parasite-evolution/scenes/` | Сцени істоти, ворогів, рівнів і UI |
| `parasite-evolution/scripts/` | Системи руху, бою, прогресу й збережень |
| `parasite-evolution/data/` | Конфігурації архетипів, мутацій, зіткнень і балансу |
| `parasite-evolution/assets/` | Імпортовані моделі, матеріали, текстури й звук |
| `parasite-evolution/source-assets/` | Вихідні художні файли та відомості про використання |
| `parasite-evolution/qa/` | Майбутні відтворювані перевірки й сценарії вимірювання |

Ці каталоги перелічені як план і не створюють хибне враження готового проєкту. Поточний коміт додає лише документацію в `docs/parasite-evolution/` і кореневий вступ.

## 2. Поділ відповідальності

| Система | Володіє станом | Приймає / видає |
| --- | --- | --- |
| `RunController` | Стан забігу, `run_id`, перемога/поразка, черга виборів | Запуск, пауза, завершення, запит мутації |
| `MovementController` | Бажана швидкість і рухове тіло | Введення, колізії, фактичний рух |
| `TargetingSystem` | Поточні валідні цілі атаки й гака | Кандидати, відстань, напрям, перевірки доступності |
| `AbilitySystem` | Поточний варіант, запуски, стан виконання й перезарядка за погодженою схемою | Окремі AB-PULL, AB-MOVE та AB-DAMAGE; не поєднує їх мовчки |
| `CombatSystem` | Атаки, унікальні контакти, бойові таймери | Запит удару, підтверджена шкода |
| `CaptureSystem` | Канал гака, слоти поглинання, резервування цілей | Захоплення, скасування, завершене поглинання |
| `HealthComponent` | Здоров'я й термінальний стан кожної цілі | Підтверджена шкода, поразка |
| `MutationSystem` | Вибрані картки й похідні характеристики | Один підтверджений вибір, нові значення характеристик |
| `EncounterDirector` | Склад груп, поява, бюджети й умови завершення | Події нейтралізації, запити підкріплення |
| `ObjectiveController` | Прогрес цілі й доступність виходу | Події вузлів, зони, боса та виходу |
| `Presentation` | Пози, щупальця, VFX, звук, HUD | Читає стан і події; не видає нагород самостійно |
| `ProfileStore` | Профіль, історія виплат, налаштування | Узгоджене збереження та читання |
| `AbilityUnlockService` | Перевірка доступності відкриття за валюту | Ціна, баланс, уже відкриті ID; одне узгоджене списання й надання доступу |

Такий поділ допомагає змінювати вид анімації без переписування правил нагород. Його не слід перетворювати на десятки порожніх абстракцій: прототипу вистачить малого набору явних компонентів.

## 3. Сцени й рух

Пропонується рухове тіло на основі `CharacterBody3D`, окремий візуальний корінь і прості форми колізій. Клас призначений для керованого скриптом руху персонажів; див. [офіційний опис](https://docs.godotengine.org/en/4.4/classes/class_characterbody3d.html).

Вороги спочатку використовують просте кероване наближення на тестовій арені. Для маршрутів навколо лабораторних перешкод оцінюємо `NavigationAgent3D` з підготовленими навігаційними даними. Агент дає інформацію про шлях; рух його батьківського об'єкта виконує наш контролер. У документації 4.4 клас позначено експериментальним, тому залежність перевіряємо на зафіксованій версії: [джерело](https://docs.godotengine.org/en/4.4/classes/class_navigationagent3d.html).

На час захоплення звичайна логіка пересування цілі призупиняється. Перенесення контролює одна система з перевіркою безпечного положення. Після відпускання маршрут перебудовується з фактичної позиції.

Під час AB-MOVE рухом героя тимчасово керує окрема фаза здібності через `MovementController`. Звичайний джойстик і ривок не переміщують корінь незалежно один від одного. Перевіряється об'єм героя, траєкторія й кінцева позиція. Після завершення, перешкоди, смерті або скасування володіння рухом повертається в узгоджений стан.

## 4. Логічні моделі даних

Це опис контрактів, а не готові класи. Конкретний формат ресурсів затверджується при реалізації.

| Модель | Основні поля | Правила |
| --- | --- | --- |
| `EntityHandle` | `id`, `generation` | Посилання на конкретний життєвий цикл; повторно використаний об'єкт пулу має нову генерацію |
| `CreatureDefinition` | `id`, базові характеристики, посилання на сцену, сокети | Незмінна конфігурація; runtime-стан зберігається окремо |
| `EnemyArchetype` | `id`, здоров'я, атака, швидкість, біомаса, захист, реакції на контроль | Ворожа роль задається даними й дозволеною поведінкою |
| `TargetState` | handle, команда, здоров'я, стан, тип цілі, власник резервування | Мертва або зарезервована ціль не отримує несумісну другу дію |
| `AttackInstance` | `attack_id`, джерело, тип, дозволені цілі, список підтверджених контактів | Один контакт по тій самій цілі не дублюється |
| `AbilityDefinition` | `id`, функція, тип цілі, дальність, cooldown, фази, формула шкоди/руху, правила переривання | Окремі визначення AB-PULL, AB-MOVE, AB-DAMAGE; незадані числа не підміняються нулями |
| `AbilityRuntime` | `cast_id`, `ability_id`, фаза, target handle/point, таймер, terminal reason | Один запуск має одне завершення; UI читає фактичний варіант |
| `AbilityUnlockDefinition` | `ability_id`, ціна в ігровій валюті, стартова доступність, ключі тексту | Ціна й початковий набір поки не затверджені; усі ID відомі |
| `AbilityUnlockTransaction` | `unlock_transaction_id`, `ability_id`, ціна операції, баланс до/після | Одне списання та одне відкриття; повтор операції не змінює стан вдруге |
| `AnchorDefinition` | `id`, позиція, доступність, дозволений підхід/приземлення | Опора AB-MOVE не прирівнюється до довільного декору чи ворога |
| `CaptureSlot` | `slot_id`, owner, target handle, фаза, час, причина скасування | Один слот має не більше однієї цілі; звільняється на всіх шляхах завершення |
| `MutationDefinition` | `id`, напрям, умови, ефекти, несумісності, ключі тексту, visual module | Вибрана картка застосовується один раз |
| `RunState` | `run_id`, seed, версія балансу, `location_id`, `zone_id`, здоров'я, біомаса, вибори, ціль | Перенесення між зонами визначає D-09; межа сама не скидає стан |
| `EncounterDefinition` | `id`, `zone_id`, групи, точки появи, бюджет, умови завершення | Рівень і налаштування появи фіксуються для конкретного зіткнення |
| `LocationDefinition` | `id`, тема, `zone_ids`, запропонований граф переходів | Групує зони однієї локації; не вимагає відкритого світу або однієї сцени |
| `ZoneDefinition` | `id`, `location_id`, рівень складності, цілі, зіткнення, профіль нагород, опори, правило доступу | Замінює проєктну назву SectorDefinition; LAB-01–LAB-05 лишаються стабільними ID |
| `ZoneProgress` | `zone_id`, відвідано, цілі завершено, перша винагорода отримана | Вхід, завершення й виплата — різні події |
| `RunResult` | `run_id`, результат, контекст локації/зон, час, причина, статистика | Після фіксації не змінюється бойовими callback |
| `RewardSettlement` | `settlement_id`, run, нагорода, перша перемога, відкриття | Атомарно застосовується до профілю один раз |
| `ProfileSave` | версія схеми, кампанія, баланс, відкриті здібності, історія виплат/відкриттів, налаштування, вигляд | Валідований і версійований; гроші гри та доступ змінюються разом |

Стабільні ID на кшталт `MUT-H1` і `LAB-01` не замінюються локалізованими назвами. Після зміни назви картки збереження й звіт усе одно знаходять її визначення.

## 5. Події та порядок обробки

Ключові події: `zone_entered`, `zone_objective_completed`, `ability_cast`, `ability_succeeded`, `ability_cancelled`, `hero_move_started`, `hero_move_finished`, `attack_confirmed`, `damage_applied`, `target_defeated`, `capture_started`, `capture_cancelled`, `consume_completed`, `biomass_changed`, `mutation_selected`, `objective_completed`, `run_finished`, `profile_committed`.

Кожна подія містить `run_id`, відповідні entity handles і потрібний ідентифікатор атаки/захоплення. Події з попереднього забігу або старої генерації об'єкта відкидаються. Візуальні слухачі не змінюють джерело бойової істини.

Порядок у такті: валідоване введення → рух і колізії → бойові контакти → зміни здоров'я й термінальні стани → завершення поглинань → біомаса й запити виборів → оновлення цілі → можливе завершення забігу → презентація. Смерть гравця має пріоритет над відкриттям нового екрана мутації чи входом у вихід у цьому самому такті.

Таймери бою використовують час симуляції та зупиняються на паузі. Статистика тривалості забігу також не включає час читання карток і пауз. Окремо можна записувати фактичну довжину сесії для власного аналізу.

Для H3 успішність пропонується визначати окремо: AB-PULL справді застосував дозволений контроль, AB-MOVE завершив дозволене переміщення, AB-DAMAGE завдав підтвердженої шкоди. Блок або скасування не мають автоматично видавати підсилення. Конкретні умови ще перевіряються прототипом.

## 6. Стартовий баланс: єдине місце чисел

Усі наведені числа — гіпотези першої реалізації. Вони не взяті з коду рекламованих ігор і ще не збалансовані. Одна одиниця відстані світу умовно відповідає метру. Старі числа гака стосуються AB-PULL; дальність, шкода й перезарядки AB-MOVE та AB-DAMAGE ще не задані й не успадковуються автоматично.

Шкода = базова шкода джерела × множник дозволеного ефекту × (1 − обмежене зменшення шкоди цілі). Напрямний щит перевіряється окремо до звичайного здоров'я. Під час реалізації чітко задаємо, які модифікатори діють на здібності.

Дробові значення допустимі у внутрішньому розрахунку; округлення видимого тексту не повинно змінювати фактичне здоров'я. Збільшення максимального здоров'я від N1 додає до поточного саме абсолютну різницю старого й нового максимуму.

Пропозиція щита: фронтальна дуга 120°, зменшення звичайної шкоди на 75% у цій дузі та блок прямого гака. Це особливість щита, а не додаток до загальної броні. Пороги фаз боса для першого тесту — 70% і 35% здоров'я; початкова фаза активна відразу.

Цих значень недостатньо для повного набору атак: радіуси, підготовка й активні фази кожного ворожого патерну визначаються при його прототипуванні. Невизначені параметри не слід приховано прирівнювати до нуля.

### 6.4. Незадані параметри нових функцій

| Варіант | Уже визначений сенс | Потребує наступного рішення |
| --- | --- | --- |
| AB-PULL | Переміщення доступного ворога; початкові числа вище — гіпотези | Остаточні числа, опір і сумісність із новою схемою керування |
| AB-MOVE | Переміщення героя до дозволеної точки | Тип опори, дальність, швидкість, cooldown, переривання й можлива невразливість |
| AB-DAMAGE | Підвищена шкода; запропоновано роль ультимейту з довшою перезарядкою | Форма удару, множник, кількість цілей, дальність, cooldown і підготовка |

Спільна перезарядка, окремі таймери, число слотів і спосіб перемикання ще не обрані в D-03. До їх визначення дані не повинні створювати видимість готових трьох одночасних здібностей. Повний опис — [розділ 13](13_SYMBIOTE_ABILITIES.md).

Відкриття за валюту вже обрано. Перед бойовим запуском перевіряється належність `ability_id` до відкритих у профілі. Витрата валюти не замінює cooldown і не повторюється при кожному застосуванні. Тестовий інструмент порівняння всіх функцій відділяється від звичайного правила доступу.

### 6.5. Розвиток і нагороди

| Параметр | Пропозиція |
| --- | --- |
| Пороги біомаси звичайного повного забігу | 10, 25, 45, 70; максимум 4 вибори |
| Перший вибір | H1, S1, B1 |
| Подальший пул | Невзяті картки обраної гілки + N1, N2, N3 |
| Кількість карток на екрані | До 3 доступних |
| Ігрова валюта | Відкриття здібностей схвалено; назва «геноматеріал» — робоча |
| Нагорода за першу / повторну перемогу | Ще визначається; попередні косметичні 25/5 не є балансом нової економіки |
| За поразку / вихід | Попереднє правило 0 потребує підтвердження D-10/D-11 |
| Початково відкрита здібність | Пропозиція AB-PULL безкоштовно; не затверджено |
| Ціна відкриття AB-MOVE | Ще не задана |
| Ціна відкриття AB-DAMAGE | Ще не задана; пропозиція дорожче AB-MOVE |

Прототип перевіряє лише перший поріг. Поточні пороги описують коротку окрему спробу; при виборі безперервного перенесення між зонами вони потребують нового розрахунку. Перетин межі не скидає біомасу приховано. Завдання не витрачають накопичений досвід.

### 6.6. Темп і профілі зон

Середній темп прогресу обраний власником. Ціни й фактичні ставки нагород ще не задані. Для налаштування потрібні час проходження, частка успішних спроб і чистий заробіток між відкриттями здібностей, а не лише номінальна нагорода за перемогу.

| Поле зони | Призначення | Статус |
| --- | --- | --- |
| `location_id` | Належність до локації, наприклад LOC-LAB | Структура обрана; конкретні ID — домовленість даних |
| `difficulty_level` | Відносний рівень небезпеки | Наявність рівня обрана; шкала 1–5 з розділу 07 є прикладом |
| `encounter_profile_id` | Склад, кількість і поєднання загроз | Потребує прототипу й перевірки |
| `reward_profile_id` | За які результати й скільки валюти видається | Ставки ще відкриті; перетин межі не дорівнює винагороді |
| `access_rule` | Вільний, послідовний або змішаний доступ | Ще не обрано в D-09 |
| `transition_policy` | Перенесення здоров'я, мутацій, таймерів і початок нової спроби | Ще не обрано; не визначається самою геометрією |

Пропонується знімок параметрів ворога при появі. Перетин межі зони не перебудовує його максимальне здоров'я або шкоду без явного правила. Нагорода за завершення має ідентифікатор результату й зони; вхід-вихід не повторює бонус першого проходження. Правила переслідування між зонами ще відкриті.

## 7. Збереження й виплати

Профіль нової гри має окреме місце збереження та версію схеми. Він не читає й не перезаписує дані Crown Rush. Настройки можна зберігати окремим простим конфігураційним файлом; Godot описує обидва підходи в [посібнику збережень](https://docs.godotengine.org/en/4.4/tutorials/io/saving_games.html).

План запису: побудувати новий валідний стан у пам'яті → серіалізувати тимчасовий файл → перевірити успішність запису → замінити основний файл контрольованою операцією → зберегти придатну резервну копію. Аварійні точки та поведінку файлових операцій перевіряємо на Android до оголошення цього механізму надійним.

Список ідентифікаторів уже застосованих виплат зберігається разом із балансом та відкриттями. При першій перемозі належність нагороди визначає поточний профіль у момент збереження. Помилка запису не дозволяє видати другу «першу перемогу» при повторі тієї самої операції.

Приклад нижче — ілюстрація контракту, а не реальний результат гри чи затверджені нагороди. Баланс 25 умовний. AB-PULL і постійні відкриття — пропозиції D-11. Список двох доступних зон показує один можливий стан; вільний або послідовний доступ ще не обрано. Комерційних платежів контракт не описує.

```json
{
  "schema_version": 1,
  "content_version": "design-0.4",
  "campaign": {
    "location_id": "LOC-LAB",
    "accessible_zone_ids": ["LAB-01", "LAB-02"],
    "cleared_zone_ids": ["LAB-01"],
    "first_clear_claimed": ["LAB-01"]
  },
  "genome_balance": 25,
  "unlocked_ability_ids": ["AB-PULL"],
  "applied_unlock_transactions": [],
  "settled_results": ["example-run-001:result"],
  "cosmetics": {
    "unlocked": ["default"],
    "selected": "default"
  },
  "settings": {
    "language": "uk",
    "music_volume": 0.7,
    "sfx_volume": 0.9,
    "haptics": true,
    "reduce_motion": false
  }
}
```

Невідома майбутня версія збереження не перетворюється мовчки на порожній профіль. Пошкоджений файл перевіряється проти резервної копії; причина показується користувачеві зрозумілою мовою. Міграції версій мають зберігати відкритий прогрес і виконуватися один раз.

У короткому прототипі відновлення середини бою поки не планується. Якщо D-09 обере довшу безперервну локацію, до реалізації визначаємо контрольні точки й відновлення між зонами. Поточний JSON не є готовим знімком живого бою.

### 7.1. Відкриття здібності як одна зміна профілю

Пропонується такий контракт: перевірити відомий `ability_id` і ціну → якщо вже відкрито, повернути поточний доступ без списання → перевірити достатній баланс → підготувати новий профіль зі списанням, ID здібності й ID операції → успішно зберегти → показати результат.

Баланс — невід'ємне ціле число ігрових одиниць. Одночасні запити обробляє один власник стану; два натиски не можуть витратити той самий залишок двічі. Повтор `unlock_transaction_id` повертає вже зафіксований результат. Нестача валюти, невідома здібність або незадана ціна нічого не списують.

Списання й відкриття не зберігаються окремими файлами без узгодженої операції. Помилка запису не показує завершене відкриття; повтор використовує той самий намір без повторного списання. Резервна копія містить узгоджені баланс та доступ. Перезапуск і поразка не повинні стирати відкриття, якщо постійну модель D-11 буде обрано.

Схема керування може дозволити одну чи кілька вже відкритих здібностей. Саме відкриття не обирає слот, не скидає бойову перезарядку й не виконує атаку.

## 8. Початкові бюджети продуктивності

Це цілі для вимірювань, а не підтверджені результати. Контрольний телефон власника можна використати для швидких перевірок; для висновку про доступність потрібен також слабший пристрій або інший узгоджений спосіб перевірки.

| Область | Початковий бюджет / ціль |
| --- | --- |
| Основний режим | Близько 60 FPS; середній кадр до 16,7 мс, p95 до 22 мс у погодженій сцені |
| Низька якість | Близько 30 FPS; середній кадр до 33,3 мс, p95 до 40 мс |
| Підвисання | Окремо рахувати кадри понад 100 мс після прогріву; ціль — відсутність у звичайному бою |
| Активні противники | Прототип до 10; зріз до 20; MVP до 40 загалом у симуляції, а не на кожну зону; стрес до 60 |
| Робочі щупальця | До 6 видимих; один канал гака й до 2 слотів поглинання |
| Істота | Початково до 8 тис. трикутників, 2 основні матеріали, до 80 кісток |
| Звичайний ворог | До 3 тис. трикутників, 1–2 матеріали, до 40 кісток |
| Бос | До 12 тис. трикутників, до 3 матеріалів, до 80 кісток |
| Текстури персонажів | Переважно 512–1024 px; більші лише після видимого обґрунтування |
| Світло й прозорість | Обмежене динамічне світло; мінімум накладених прозорих шарів |

Трикутники й кістки самі не визначають FPS. Вимірюємо CPU/GPU, число матеріалів, тіней, прозорих ефектів і вартість навігації. Для повторюваного декору можна оцінити `MultiMesh`; автоматичне інстансування Forward+ не слід вважати доступним у Mobile renderer. Цю різницю прямо описує [посібник Godot](https://docs.godotengine.org/en/4.4/tutorials/performance/optimizing_3d_performance.html).

Профіль «низька якість» скорочує декоративні частинки, тіні й деталізацію. Він зберігає видимі бойові попередження та не змінює правила влучання.

## 9. Локальні звіти

Звіт містить версію збірки, баланс, `location_id`, `zone_id`, рівень зони, seed, час без пауз, гілку, картки, активний `ability_id`, шкоду, результати здібностей, заробіток, переходи, результат і зведені кадри. Це дозволяє порівнювати темп і ризик у різних зонах; дані потрібні для аналізу, а не як технічний текст у HUD.

У базовому офлайн дизайні звіт не надсилається автоматично. Експорт — явна дія користувача. Не включаємо токени, приватні шляхи, контакти або інші сторонні дані. Seed відтворює вибір контенту, але не обіцяє повністю детермінований replay фізики.

## 10. Android-збірка й подальша інтеграція

На етапі прототипу потрібен окремий debug APK з власними назвою та ідентифікатором пакета. Він не повинен встановлюватися поверх Crown Rush. Точний package ID, підпис і спосіб публікації визначаємо перед налаштуванням нового експорту.

Поточна документаційна гілка не змінює workflow, ключі або налаштування експорту. Майбутній CI має збирати саме новий шлях проєкту та видавати окремо названий артефакт. Публікація в магазин, релізний підпис та магазинні матеріали — наступний окремий етап після перевірки гри.
