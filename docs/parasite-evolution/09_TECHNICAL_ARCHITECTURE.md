# 09. Технічна архітектура, моделі даних і стартові числа

Статус: технічний план v0.10. Погоджено Unity/C#/URP, альбомне керування B-02, смерть із сейв-зоною й частковою втратою валюти. Реалізації ще немає; B-01 і непоказані технічні деталі лишаються пропозиціями.

## 1. Рушій і структура репозиторію

Для нової гри погоджено Unity 6.3 LTS, C#, URP та обидві горизонтальні орієнтації. Точний Editor patch і версії пакетів ще фіксуємо. Див. [розділ 16](16_UNITY_LANDSCAPE.md).

У перевіреному Crown Rush використовується Godot 4.4.1. Це історичний стан іншої гри, а не налаштування майбутньої Unity-збірки.

| Майбутній шлях | Вміст |
| --- | --- |
| `parasite-evolution/Assets/_Game/Scenes/` | Bootstrap, постійна сцена, тестова кімната, блоки світу |
| `parasite-evolution/Assets/_Game/Prefabs/` | Герой, вороги, здібності, сейв-зони, UI |
| `parasite-evolution/Assets/_Game/Scripts/` | C#-системи й компоненти |
| `parasite-evolution/Assets/_Game/Data/` | ScriptableObject-визначення та баланс, окремо від runtime-стану |
| `parasite-evolution/Assets/_Game/Art/` | FBX, матеріали, текстури, анімації |
| `parasite-evolution/Packages/` | Пакети й lock-файл |
| `parasite-evolution/ProjectSettings/` | Версія редактора, renderer, Android та input |

Це запропонована структура; каталог Unity з виконуваним проєктом ще не створений. Майбутні вихідні асети зберігаються зі своїми `.meta`; кеші редактора не є вихідним кодом.

## 2. Поділ відповідальності

| Система | Володіє станом | Приймає / видає |
| --- | --- | --- |
| `WorldController` | `world_id`, стан героя, пауза, загибель, черга розвитку | Продовження світу, локальні події; завершення цілі не зупиняє весь світ |
| `WorldStreaming` | Завантажені блоки й бойові посилання, які їх утримують | Підготовка геометрії/навігації, запис стану й контрольоване вивантаження |
| `MovementController` | Бажана швидкість і рухове тіло | Введення, колізії, фактичний рух |
| `TargetingSystem` | Поточні валідні цілі атаки й гака | Кандидати, відстань, напрям, перевірки доступності |
| `AbilitySystem` | Поточний варіант, запуски, стан виконання й перезарядка за погодженою схемою | Окремі AB-PULL, AB-MOVE та AB-DAMAGE; не поєднує їх мовчки |
| `CombatSystem` | Атаки, унікальні контакти, бойові таймери | Запит удару, підтверджена шкода |
| `CaptureSystem` | Канал гака, слоти поглинання, резервування цілей | Захоплення, скасування, завершене поглинання |
| `HealthComponent` | Здоров'я й термінальний стан кожної цілі | Підтверджена шкода, поразка |
| `MutationSystem` | Вибрані картки й похідні характеристики | Один підтверджений вибір, нові значення характеристик |
| `EncounterDirector` | Склад груп, поява, бюджети й умови завершення | Події нейтралізації, запити підкріплення |
| `ObjectiveController` | Стан локальних цілей у світі | Події об'єктів і боса; результат не закриває сусідні регіони |
| `Presentation` | Пози, щупальця, VFX, звук, HUD | Читає стан і події; не видає нагород самостійно |
| `ProfileStore` | Профіль, історія виплат, налаштування | Узгоджене збереження та читання |
| `AbilityUnlockService` | Перевірка доступності відкриття за валюту | Ціна, баланс, уже відкриті ID; одне узгоджене списання й надання доступу |
| `DeathRecoveryController` | Одна подія смерті, штраф і незавершене повернення | Запис урегулювання, підготовка сейв-зони, відновлення без повторного списання |

Такий поділ допомагає змінювати вид анімації без переписування правил нагород. Його не слід перетворювати на десятки порожніх абстракцій: прототипу вистачить малого набору явних компонентів.

## 3. Unity-сцени, рух та підвантаження

Пропонується `CharacterController` для героя, візуальна дочірня ієрархія з Animator і власними відростками, а для звичайної навігації ворогів — `NavMeshAgent`. Під час тяги лише один контролер володіє позицією цілі; агент не бореться з примусовим переміщенням. Джерела API й план тесту — [розділ 16](16_UNITY_LANDSCAPE.md).

Постійна сцена утримує героя й сервіси; блоки світу пропонується завантажувати additively. Планувальник блоків і стан об'єктів реалізуються нашою C#-логікою. Навігація та опори гака мають бути готові до входу в блок.

AB-MOVE тимчасово володіє рухом героя. Джойстик, ривок і перенесення після смерті не рухають один корінь незалежно. Смерть скасовує нові бойові дії та безпечно звільняє живі посилання. Місце відновлення перевіряється після підготовки сейв-зони.

## 4. Логічні моделі даних

Це опис контрактів, а не готові класи. Конкретний формат ресурсів затверджується при реалізації.

| Модель | Основні поля | Правила |
| --- | --- | --- |
| `EntityHandle` | `id`, `generation` | Посилання на конкретний життєвий цикл; повторно використаний об'єкт пулу має нову генерацію |
| `CreatureDefinition` | `id`, базові характеристики, посилання на сцену, сокети | Незмінна конфігурація; runtime-стан зберігається окремо |
| `EnemyArchetype` | `id`, здоров'я, атака, швидкість, біомаса, захист, реакції на контроль | Ворожа роль задається даними й дозволеною поведінкою |
| `TargetState` | handle, команда, здоров'я, стан, тип цілі, власник резервування | Мертва або зарезервована ціль не отримує несумісну другу дію |
| `AttackInstance` | `attack_id`, джерело, тип, дозволені цілі, список підтверджених контактів | Один контакт по тій самій цілі не дублюється |
| `AbilityDefinition` | `id`, функція, тип цілі, дальність, cooldown, фази, формула шкоди/руху, правила переривання | Окремі визначення AB-PULL, AB-MOVE, AB-DAMAGE; незадані числа не підміняються нулями |
| `AbilityRuntime` | `cast_id`, `ability_id`, фаза, target handle/point, таймер, terminal reason | Один запуск має одне завершення; UI читає фактичний варіант |
| `AbilityUnlockDefinition` | `ability_id`, ціна в ігровій валюті, стартова доступність, ключі тексту | Ціна й початковий набір поки не затверджені; усі ID відомі |
| `AbilityUnlockTransaction` | `unlock_transaction_id`, `ability_id`, ціна операції, баланс до/після | Одне списання та одне відкриття; повтор операції не змінює стан вдруге |
| `SafeZoneDefinition` | `id`, зона, валідна поза появи, правило активації й захисту | Категорія сейв-зони обрана; конкретні сервіси й вибір точки — B-01 |
| `DeathPolicy` | версія, частка штрафу, округлення, вибір сейву, правила стану героя | Часткова втрата обрана; 10% і додаткові параметри лише запропоновані |
| `DeathSettlement` | `death_id`, `world_id`, баланс до, втрата, сейв, незавершене повернення | Одна смерть — одне списання, навіть після перезапуску |
| `AnchorDefinition` | `id`, позиція, доступність, дозволений підхід/приземлення | Опора AB-MOVE не прирівнюється до довільного декору чи ворога |
| `CaptureSlot` | `slot_id`, owner, target handle, фаза, час, причина скасування | Один слот має не більше однієї цілі; звільняється на всіх шляхах завершення |
| `MutationDefinition` | `id`, напрям, умови, ефекти, несумісності, ключі тексту, visual module | Вибрана картка застосовується один раз |
| `WorldState` | `world_id`, seed, версія контенту, відвідані зони, цілі, життєві цикли об'єктів | Живе між переходами й погодженими збереженнями |
| `PlayerState` | Здоров'я, біомаса, мутації, активні функції, таймери, точка повернення | Перехід зони не скидає; смерть переносить у сейв-зону зі штрафом, решта параметрів B-01 ще відкриті |
| `SessionStats` | `session_id`, час, маршрут, виміри й результат сесії | Аналітична межа сесії не створює новий світ |
| `EncounterDefinition` | `id`, `zone_id`, групи, точки появи, бюджет, умови завершення | Рівень і налаштування появи фіксуються для конкретного зіткнення |
| `LocationDefinition` | `id`, тема, `zone_ids`, граф доступних маршрутів | Групує зони відкритого світу; основні зони досяжні базовим рухом |
| `ZoneDefinition` | `id`, `location_id`, рівень складності, цілі, зіткнення, профіль нагород, опори, правило доступу | Замінює проєктну назву SectorDefinition; LAB-01–LAB-05 лишаються стабільними ID |
| `ZoneProgress` | `zone_id`, відвідано, цілі завершено, перша винагорода отримана | Вхід, завершення й виплата — різні події |
| `ActivityResult` | `world_id`, `activity_instance_id`, зона, результат, підтверджені джерела | Локальна подія не завершує світ; повторне читання не створює другу нагороду |
| `RewardSettlement` | `settlement_id`, `world_id`, `reward_event_id`, нагорода й пов'язаний стан цілі | Одноразово застосовується до узгодженого збереження |
| `ProfileSave` | версія схеми, кампанія, баланс, відкриті здібності, історія виплат/відкриттів, налаштування, вигляд | Валідований і версійований; гроші гри та доступ змінюються разом |

Стабільні ID на кшталт `MUT-H1` і `LAB-01` не замінюються локалізованими назвами. Після зміни назви картки збереження й звіт усе одно знаходять її визначення.

## 5. Події та порядок обробки

Ключові події: `world_loaded`, `world_saved`, `zone_entered`, `activity_completed`, `ability_cast`, `ability_succeeded`, `ability_cancelled`, `hero_move_started`, `hero_move_finished`, `attack_confirmed`, `damage_applied`, `target_defeated`, `capture_started`, `capture_cancelled`, `consume_completed`, `biomass_changed`, `mutation_selected`, `player_defeated`, `profile_committed`.

Події містять `world_id`, контекст зони, entity handles і потрібний ID атаки/захоплення. Стара генерація об'єкта або інший світ не отримують відкладену дію. `session_id` потрібний для звіту; нова сесія не створює нову винагороду за стару ціль. Візуальні слухачі не змінюють бойову істину.

Порядок у такті: введення → рух і колізії → бойові контакти → здоров'я й термінальні стани → поглинання → розвиток → локальні цілі й облік нагород → презентація. Загибель зупиняє нові дії героя й відкриття нового вибору; правило винагороди при одночасній загибелі й завершенні цілі ще визначає D-10. Перехід зони не є термінальним станом.

Таймери бою використовують час симуляції та зупиняються на паузі. Статистика тривалості забігу також не включає час читання карток і пауз. Окремо можна записувати фактичну довжину сесії для власного аналізу.

Для H3 успішність пропонується визначати окремо: AB-PULL справді застосував дозволений контроль, AB-MOVE завершив дозволене переміщення, AB-DAMAGE завдав підтвердженої шкоди. Блок або скасування не мають автоматично видавати підсилення. Конкретні умови ще перевіряються прототипом.

## 6. Стартовий баланс: єдине місце чисел

Усі наведені числа — гіпотези першої реалізації. Вони не взяті з коду рекламованих ігор і ще не збалансовані. Одна одиниця відстані світу умовно відповідає метру. Старі числа гака стосуються AB-PULL; дальність, шкода й перезарядки AB-MOVE та AB-DAMAGE ще не задані й не успадковуються автоматично.

### 6.1. Базова істота й контакт

| Параметр | Стартове значення |

| Максимальне здоров'я | 100 |
| Швидкість руху | 5 м/с |
| Радіус основної колізії | 0,45 м |
| Шкода базового удару | 12 |
| Інтервал базових атак | 0,75 с |
| Підготовка базового удару | 0,18 с; входить в інтервал |
| Радіус базової атаки | 2 м |
| Дальність AB-PULL | 8 м |

| Швидкість наконечника AB-PULL | 24 м/с |
| Тривалість притягування AB-PULL | 0,15–0,45 с залежно від дистанції |
| Базова кількість слотів поглинання | 1 |
| Дальність початку поглинання | 2,5 м |
| Максимальна дистанція утримання поглинання | 3,5 м; далі скасування |
| Тривалість поглинання | 0,75 с |
| Мінімальний допустимий час після модифікаторів | 0,35 с |
| Короткий захист після шкоди | 0,15 с; перевірити, чи потрібен |

Шкода = базова шкода джерела × множник дозволеного ефекту × (1 − обмежене зменшення шкоди цілі). Напрямний щит перевіряється окремо до звичайного здоров'я. Під час реалізації чітко задаємо, які модифікатори діють на здібності.

Дробові значення допустимі у внутрішньому розрахунку; округлення видимого тексту не повинно змінювати фактичне здоров'я. Збільшення максимального здоров'я від N1 додає до поточного саме абсолютну різницю старого й нового максимуму.

Пропозиція щита: фронтальна дуга 120°, зменшення звичайної шкоди на 75% у цій дузі та блок прямого гака. Це особливість щита, а не додаток до загальної броні. Пороги фаз боса для першого тесту — 70% і 35% здоров'я; початкова фаза активна відразу.

Цих значень недостатньо для повного набору атак: радіуси, підготовка й активні фази кожного ворожого патерну визначаються при його прототипуванні. Невизначені параметри не слід приховано прирівнювати до нуля.

### 6.4. Незадані параметри нових функцій

| Варіант | Уже визначений сенс | Потребує наступного рішення |
| --- | --- | --- |
| AB-PULL | Переміщення доступного ворога; початкові числа вище — гіпотези | Остаточні числа, опір і сумісність із новою схемою керування |
| AB-MOVE | Переміщення героя до дозволеної точки | Тип опори, дальність, швидкість, cooldown, переривання й можлива невразливість |
| AB-DAMAGE | Підвищена шкода; запропоновано роль ультимейту з довшою перезарядкою | Форма удару, множник, кількість цілей, дальність, cooldown і підготовка |

У D-03 погоджено до трьох правих кнопок відкритих функцій із окремими таймерами. Числа, прицілювання та взаємне переривання виконання ще відкриті. UI й дані повинні розрізняти відкриття, готовність і поточний запуск кожної функції. Повний опис — [розділ 13](13_SYMBIOTE_ABILITIES.md).

Відкриття за валюту вже обрано. Перед бойовим запуском перевіряється належність `ability_id` до відкритих у профілі. Витрата валюти не замінює cooldown і не повторюється при кожному застосуванні. Тестовий інструмент порівняння всіх функцій відділяється від звичайного правила доступу.

### 6.5. Розвиток і нагороди

| Параметр | Пропозиція |
| --- | --- |
| Пороги біомаси ізольованої тестової сцени | 10, 25, 45, 70; 4 вибори лише для прототипу; довгостроковий світ потребує перегляду D-07 |
| Перший вибір | H1, S1, B1 |
| Подальший пул | Невзяті картки обраної гілки + N1, N2, N3 |
| Кількість карток на екрані | До 3 доступних |
| Ігрова валюта | Відкриття здібностей схвалено; назва «геноматеріал» — робоча |
| Нагорода за першу / повторну перемогу | Ще визначається; попередні косметичні 25/5 не є балансом нової економіки |
| Після смерті | Часткова втрата поточного накопиченого балансу; частка ще не обрана; пропозиція 10% |
| Сейв-зона після смерті | Перенесення обране; остання активована точка — пропозиція B-01 |
| Початково відкрита здібність | Пропозиція AB-PULL безкоштовно; не затверджено |
| Ціна відкриття AB-MOVE | Ще не задана |
| Ціна відкриття AB-DAMAGE | Ще не задана; пропозиція дорожче AB-MOVE |

Прототип перевіряє перший поріг. Для обраного відкритого світу довгострокові пороги, ліміт мутацій і зміна гілки ще визначає D-07. Старі чотири вибори не оголошуються готовою еволюцією на весь світ. Межа зони зберігає біомасу; завдання не витрачають її.

### 6.6. Темп і профілі зон

Середній темп прогресу обраний власником. Ціни й фактичні ставки нагород ще не задані. Для налаштування потрібні час проходження, частка успішних спроб і чистий заробіток між відкриттями здібностей, а не лише номінальна нагорода за перемогу.

| Поле зони | Призначення | Статус |
| --- | --- | --- |
| `location_id` | Належність до локації, наприклад LOC-LAB | Структура обрана; конкретні ID — домовленість даних |
| `difficulty_level` | Відносний рівень небезпеки | Наявність рівня обрана; шкала 1–5 з розділу 07 є прикладом |
| `encounter_profile_id` | Склад, кількість і поєднання загроз | Потребує прототипу й перевірки |
| `reward_profile_id` | За які результати й скільки валюти видається | Ставки ще відкриті; перетин межі не дорівнює винагороді |
| `access_rule` | Вільний доступ до основних зон | Обрано: open; проходження попередньої зони й оплата не є вимогою |
| `transition_policy` | Безперервне перенесення героя | Здоров'я, мутації, біомаса й таймери продовжуються; смерть і відновлення — окреме D-10 |

Пропонується знімок параметрів ворога при появі. Перетин межі зони не перебудовує його максимальне здоров'я або шкоду без явного правила. Нагорода за завершення має ідентифікатор результату й зони; вхід-вихід не повторює бонус першого проходження. Правила переслідування між зонами ще відкриті.

## 7. Збереження відкритого світу й виплати

Нова гра має власні дані та не перезаписує Crown Rush. Пропонується узгоджений знімок профілю, героя та прогресу світу. Для локального шляху Unity пропонується [Application.persistentDataPath](https://docs.unity3d.com/6000.3/Documentation/ScriptReference/Application-persistentDataPath.html). Конкретний JSON-виконавець і узгоджений контракт створюємо та перевіряємо окремо.

План запису: підготувати новий стан → серіалізувати тимчасовий файл → перевірити успіх → контрольовано замінити основний файл → зберегти придатну резервну копію. Аварійні точки перевіряються на Android.

Винагорода за об'єкт має стабільний світовий ID. ID сесії, перехід і повторне підвантаження не дозволяють видати її знову. Власність здібності, баланс і пов'язаний стан локальної цілі записуються узгоджено.

Приклад — ілюстрація контракту. Баланс, мутація й точки умовні. Після смерті обрані сейв-зона й часткова втрата валюти; відсоток і додатковий стан героя ще обговорюються. null у death_recovery означає відсутність незавершеного повернення.

```json
{
  "schema_version": 1,
  "content_version": "design-0.10",
  "world": {
    "world_id": "example-world-001",
    "location_id": "LOC-LAB",
    "current_zone_id": "LAB-01",
    "last_safe_zone_id": "example-safe-zone",
    "visited_zone_ids": ["LAB-01", "LAB-02"],
    "completed_objective_ids": ["example-objective-001"]
  },
  "player": {
    "health": 100,
    "biomass": 10,
    "mutation_ids": ["MUT-H1"],
    "resume_point_id": "example-safe-point"
  },
  "genome_balance": 25,
  "unlocked_ability_ids": ["AB-PULL"],
  "applied_unlock_transactions": [],
  "applied_death_ids": [],
  "death_recovery": null,
  "claimed_reward_event_ids": ["example-world-001:example-objective-001:first"],
  "cosmetics": {
    "unlocked": ["default"],
    "selected": "default"
  },
  "settings": {
    "language": "uk",
    "music_volume": 0.7,
    "sfx_volume": 0.9,
    "haptics": true,
    "reduce_motion": false
  }
}
```

Пропонується зберігати стан у безпечних точках і після значущих змін прогресу. Економічні операції мають власне негайне узгоджене збереження. Точний живий гак/контроль ворога при аварійному завершенні ще не серіалізований; не обіцяємо покадрове відновлення.

Невідома майбутня версія або пошкоджений файл не стирають прогрес мовчки. Перевіряємо резервну копію й показуємо зрозумілий результат відновлення. Міграції зберігають уже отриманий доступ.

### 7.1. Відкриття здібності як одна зміна профілю

Пропонується такий контракт: перевірити відомий `ability_id` і ціну → якщо вже відкрито, повернути поточний доступ без списання → перевірити достатній баланс → підготувати новий профіль зі списанням, ID здібності й ID операції → успішно зберегти → показати результат.

Баланс — невід'ємне ціле число ігрових одиниць. Одночасні запити обробляє один власник стану; два натиски не можуть витратити той самий залишок двічі. Повтор `unlock_transaction_id` повертає вже зафіксований результат. Нестача валюти, невідома здібність або незадана ціна нічого не списують.

Списання й відкриття не зберігаються окремими файлами без узгодженої операції. Помилка запису не показує завершене відкриття; повтор використовує той самий намір без повторного списання. Резервна копія містить узгоджені баланс та доступ. Перезапуск і поразка не повинні стирати відкриття, якщо постійну модель D-11 буде обрано.

Схема керування може дозволити одну чи кілька вже відкритих здібностей. Саме відкриття не обирає слот, не скидає бойову перезарядку й не виконує атаку.

## 8. Початкові бюджети продуктивності

Це цілі для вимірювань, а не підтверджені результати. Контрольний телефон власника можна використати для швидких перевірок; для висновку про доступність потрібен також слабший пристрій або інший узгоджений спосіб перевірки.

| Область | Початковий бюджет / ціль |
| --- | --- |
| Основний режим | Близько 60 FPS; середній кадр до 16,7 мс, p95 до 22 мс у погодженій сцені |
| Низька якість | Близько 30 FPS; середній кадр до 33,3 мс, p95 до 40 мс |
| Підвисання | Окремо рахувати кадри понад 100 мс після прогріву; ціль — відсутність у звичайному бою |
| Активні противники | Прототип до 10; зріз до 20; MVP до 40 загалом у симуляції, а не на кожну зону; стрес до 60 |
| Робочі щупальця | До 6 видимих; один канал гака й до 2 слотів поглинання |
| Істота | Початково до 8 тис. трикутників, 2 основні матеріали, до 80 кісток |
| Звичайний ворог | До 3 тис. трикутників, 1–2 матеріали, до 40 кісток |
| Бос | До 12 тис. трикутників, до 3 матеріалів, до 80 кісток |
| Текстури персонажів | Переважно 512–1024 px; більші лише після видимого обґрунтування |
| Світло й прозорість | Обмежене динамічне світло; мінімум накладених прозорих шарів |

Трикутники й кістки не визначають FPS самі. У Unity-проєкті вимірюємо CPU/GPU, матеріали, прозорість, тіні, анімацію й навігацію. URP-профілі та варіанти повторного малювання добираємо за вимірами. Старі Godot-специфічні припущення про renderer не переносяться на Unity.

Профіль «низька якість» скорочує декоративні частинки, тіні й деталізацію. Він зберігає видимі бойові попередження та не змінює правила влучання.

## 9. Локальні звіти

Звіт містить версію, `world_id`, `session_id`, маршрут зон, їх рівні, seed, час без пауз, мутації, здібності, шкоду, заробіток, результати локальних цілей і зведені кадри. Для відкритого формату окремо вимірюємо підвантаження та повернення. Технічні ID не виводяться в ігровий HUD.

У базовому офлайн дизайні звіт не надсилається автоматично. Експорт — явна дія користувача. Не включаємо токени, приватні шляхи, контакти або інші сторонні дані. Seed відтворює вибір контенту, але не обіцяє повністю детермінований replay фізики.

## 10. Альбомний Android і збірка

Робочий напрям — горизонтальний екран. Пропонується підтримати Landscape Left/Right, адаптувати safe area й скидати старі дотики після повороту. Портретний HUD більше не є цільовим. Число кнопок і камера — B-02.

Для реалізації потрібні зафіксований Unity Editor, Android build support і власний ідентифікатор нової гри. У власника лише Android: код і GitHub можна вести з телефона, Editor та збірка працюватимуть у зовнішньому підтримуваному середовищі. Конкретна машина, активація й CI ще не налаштовані. Передумови та варіанти — [розділ 17](17_ANDROID_ONLY_WORKFLOW.md).

Поточний коміт змінює документацію. Наявний Godot workflow не оголошується Unity pipeline; майбутня збірка готується окремо з новим шляхом і власним артефактом.

## 11. Підвантаження й стан блоків

Блок пам'яті та зона складності — різні одиниці. Пропонується наш компонент підвантаження з підготовкою геометрії, навігації й об'єктів попереду героя. Це майбутній код, а не вже готова функція проєкту.

Активний гак, поглинання, ціль атаки або опора ривка утримують потрібний блок. Вивантаження дозволяється після безпечного звільнення посилань і запису потрібного стану. Повернення не відновлює вже виданий одноразовий ресурс.

Початковий тест: кілька зв'язних зон, рух туди й назад, ціль на межі, повернення після збереження та глобальний бюджет акторів. Сам прогін окремої кімнати не перевіряє цей контракт. Деталі — [розділ 14](14_OPEN_WORLD.md).

## 12. Урегулювання смерті й повернення

Погоджено сейв-зону й часткову втрату валюти. Налаштовувана частка ще не задана; 10% — кандидат B-01, не затверджений default. Для часткового штрафу потрібна частка між нулем і одиницею; приклад формули й округлення — [розділ 15](15_DEATH_SAFE_ZONES_AND_BLOCKS.md).

План: створити один death_id → обчислити штраф за погодженою версією політики → узгоджено зберегти баланс після списання, death_id і pending recovery → підготувати валідну сейв-зону → відновити героя за погодженим станом → завершити recovery. Перезапуск після списання продовжує ту саму операцію без другого штрафу.

WorldDefinition має валідну стартову сейв-зону як технічний fallback, якщо збережена точка недоступна. Відсоток, вибір останнього/найближчого сейву, здоров'я, мутації й таймери після повернення ще належать B-01. Створення нового світу або повторна видача перших нагород не є частиною смерті.

## 13. Контракт слизової форми й втяжних щупалець

Погоджено: аморфна слизова маса, гострі втяжні щупальця, слабкий згин і основний рух через видовження та скорочення. Немає фіксованого радіального віяла або заданих восьми кінцівок.

Пропонується `TendrilLocomotionController`, який планує висування, закріплення, скорочення, відпускання й втягування. Фаза опори формує бажане зміщення тіла, а `MovementController` застосовує його з перевіркою колізій. Один власник змінює позицію; Animator і декоративні сегменти не створюють паралельного переміщення.

`TendrilState`: роль, фаза, точка основи, `anchor_handle`, контакт наконечника, поточна/цільова/максимальна довжина, обмеження згину. Для статичної опори точка наконечника фіксується у світі; для рухомої цілі вона відстежує валідований об'єкт. Після відпускання handle очищається. Повне втягування ховає геометрію й не залишає контакту або hitbox.

AB-MOVE швидко скорочує довжину до опори та переміщує героя; звичайні опорні фази тимчасово поступаються керуванням. AB-PULL утримує героя іншими опорами та переміщує ціль; NavMeshAgent не володіє її позицією одночасно. Гра не отримує вільного проходження крізь стіни від самого видовження щупальця.

Презентація читає цей стан і деформує слизову масу та щупальця. Згин обмежений; довга хвиляста крива не є головним анімаційним параметром. Точні швидкості, довжини, число опор, числовий bend limit та реалізація mesh-деформації ще не вибрані. Це план, виконуваного Unity-коду ще немає.
